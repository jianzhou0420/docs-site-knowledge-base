Conventions

The operating rules for this scaffold. Read once, apply mechanically thereafter.

1. The filesystem IS the nav

Every directory under docs/pages/ becomes a top tab. Every .html file becomes a page. You never maintain a central nav list.

  • Drop a new directory docs/pages/<x>/ with an index.html → a new tab appears.
  • Drop a new .html file into a tab → a new sidebar entry appears.
  • Move or rename a file → its nav entry and URL move with it.

Directories and files whose names start with _ or . are skipped by the scanner — that's how _lib/, _tab.json, and _site.json stay out of the nav.

2. _tab.json is for overrides only

Each tab may carry a docs/pages/<tab>/_tab.json. It never adds pages — it only adjusts how discovered pages are presented. All fields are optional:

FieldEffect
labelTab text in the header (default: title-cased directory name).
keyCSS accent class for the tab (default: directory name).
landingPage the tab opens to, relative to the tab dir (default: index.html).
order_prioritySmaller = further left in the tab strip (default: 100).
sectionsCurated sidebar groups (see §6). Omit to auto-discover one section per subdirectory.
external_layouttrue = the tab's pages own their chrome; the wrap script leaves them alone (see §10).

If alphabetical order is fine and the directory name title-cases well, skip the file entirely.

3. Two-to-five tabs is the sweet spot

One tab feels undercooked; six or more crowds the bar. Pick 2–5 top-level directories. Tab order is by order_priority (then directory name) — set it explicitly in each _tab.json rather than relying on the default.

4. The root landing is docs/index.html

The bare URL / serves docs/index.html directly — there is no redirect plugin and no magic. Edit that file to be your welcome page, or replace its body with a link hub. It is wrapped with the same chrome as every other page (its breadcrumb root is the site name; its right-TOC is suppressed).

5. Author inside <main class="doc-body">

Every page you write is a normal HTML document whose authored content lives in a single <main class="doc-body">…</main> block, with a <title> in the head. The wrap script extracts exactly that block and re-renders the full page around it. Rules that make a page behave:

  • The <title> sets the browser title and the sidebar/breadcrumb label. Don't add the site-name suffix yourself — the wrapper does.
  • Give section headings an id (<h2 id="overview">). The on-this-page TOC is built from <h2 id> and <h3 id>.
  • Page-specific <style> in the head and trailing <script> blocks are preserved across re-wraps.

6. Bake the chrome after structural changes

The dev server reloads content live, but the header/sidebar/breadcrumbs/TOC are baked in at author time. After you add, move, rename, or retitle a page — or change the layout, branding, or a _tab.json — re-run:

python3 docs/_lib/_wrap_handwritten.py

It is idempotent: running it twice produces no further change, and it won't double-escape titles or stack footers. A page is recognised by its <main class="doc-body"> block, so the operation is safe to repeat.

Curated sidebar sections

A tab's sidebar is built from its sections. Each section names a directory (relative to the tab) and may pin an order of file stems:

"sections": [
  {"label": "Getting Started", "dir": "getting-started", "key": "guide"},
  {"label": "Reference", "dir": "reference", "key": "guide",
   "order": ["concepts", "api"]}
]

A section with "dir": "" points at the tab root itself — that's how a flat tab (files directly under the tab dir, no subfolders) renders a sidebar, as both tabs in this site do. Omit sections entirely and the scanner auto-creates one section per subdirectory.

7. assets/ and _lib/ are invisible to the nav

The scanner only looks under docs/pages/, and skips _/. names. So docs/assets/ (CSS/JS/images), docs/_lib/ (the engine), and the _*.json config files never become tabs. Reference assets with a path relative to the page; the wrap script computes the correct ../ prefix for the layout's own asset links.

8. Cross-page links use relative paths

Link between pages with ordinary relative hrefs ending in .html:

<a href="../recipes/add-a-tab.html">Add a tab</a>

When you move a directory, cross-boundary links break. There's no strict-build checker shipped, so grep for the old path after a move: grep -rn 'old-folder/' docs/pages/.

9. Branding lives in docs/_site.json

Site name, tagline, footer, and logo target are read from _site.json by the layout and nav code — never hardcode them in _lib/. Change the name there, re-wrap, and the logo, <title> suffix, breadcrumb root, and footer all update together.

10. external_layout for self-chromed pages

Some pages own their full markup — a Reveal.js deck, a generated report, an embedded app. Mark their tab with "external_layout": true in _tab.json; the wrap script then skips that tab entirely, leaving its HTML untouched while the tab still appears in the header. See Recipes → Include an HTML deck.
